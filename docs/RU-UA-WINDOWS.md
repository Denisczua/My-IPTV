# RU/UA: проверка и использование в Чехии

## Что готово сейчас

Исходный `playlist.m3u` не изменяется скриптами RU/UA. Полностью прочитаны
11 438 записей. Отобраны 708 записей: 561 с русским языком и 167 с украинским,
из них 20 имеют оба языка. Эти числа считают записи/варианты потоков, а не
уникальные бренды телеканалов. Все 708 пока имеют статус `UNKNOWN_CZ`.
94 многоязычные записи требуют проверки преобладающего языка и не отобраны;
10 636 имеют другой язык. Записей совсем без языковых данных в этом снимке нет.

`playlist-ru-ua-testing.m3u` содержит 708 потоков в 733 записях категорий для диагностики. Проверка
воспроизведения и фактическая доступность из Чехии пока не проводились.
`playlist-ru-ua.m3u` намеренно ещё не создан: пустой основной плейлист
публиковать запрещено. Он автоматически появится после накопления `STABLE_CZ`.

## Языки и сохранность записей

Основной источник языка — `languages` для точного `tvg-id` с суффиксом версии
в [IPTV-org feeds API](https://iptv-org.github.io/api/feeds.json).
Сохраняется сокращённый снимок этих данных с URL источника и датой загрузки.
При отсутствии точных данных используются `tvg-language`, URL и идентификаторы
из [русской](https://iptv-org.github.io/iptv/languages/rus.m3u) и
[украинской](https://iptv-org.github.io/iptv/languages/ukr.m3u) подборок.
Страна и кириллическое название сами по себе не доказывают язык.
Метаданные могут ошибаться; это языковая классификация, не распознавание звука.
Если среди известных языков есть другие, автоматически определить преобладание
RU/UA нельзя: такая запись требует отдельного подтверждения.

Ручные уточнения: `data/language-overrides.json`, ключ — полный URL потока либо
идентификатор канала без `@HD`. Значение, например:

```json
{
  "Example.us": {
    "languages": ["rus"],
    "evidence": "https://official-channel.example/language-policy"
  }
}
```

Используйте действительный источник, подтверждающий преобладающий язык.
Для исключения укажите пустой массив `languages` и причину в `evidence`.

Ручные каналы лучше добавлять в отдельный `playlist-ru-ua-manual.m3u` с обычным
заголовком `#EXTM3U`. Файл не создаётся пустым. Если рабочие записи уже вручную
добавлены в основной/диагностический плейлист, они импортируются в базу перед
перегенерацией. Без подтверждённого языка и чешских проверок автоматически
в основной плейлист они не попадут, но будут сохранены в базе.

База `data/ru-ua-state.json` сохраняет исходные блоки M3U и всю историю проверок,
включая исчезнувшие из источника, исключённые по языку и OFFLINE-записи.
Название, логотип, URL и директивы HTTP сохраняются. Исходная группа остаётся
в базе; в выходном M3U `group-title` меняется на соответствующую категорию.
Идентичность учитывает URL, атрибуты и HTTP-заголовки, но не категорию:
другой поток проверяется отдельно, копии в разных группах не размножают базу.
Заголовок и глобальные опции источника
сохраняются; фактическая поддержка отдельных директив зависит от OTTPlayer.

## Подготовка Windows позднее

1. Установите бесплатные Python 3.12 или новее, Git и FFmpeg. Включите Python,
   Git, `ffmpeg.exe` и `ffprobe.exe` в `PATH`. Источники:
   [Python](https://www.python.org/downloads/windows/),
   [Git](https://git-scm.com/downloads/win),
   [FFmpeg](https://ffmpeg.org/download.html#build-windows).
   Сторонние Python-библиотеки не нужны.
2. Используйте обычное подключение компьютера в Чехии. Выключите VPN, прокси
   и средства изменения региона. Скрипт не умеет доказывать отсутствие
   системного VPN: параметр `--confirm-direct-cz` — ваше подтверждение прямого
   подключения. Геолокация двух независимых сервисов должна совпасть: CZ и один IP.
3. Сохраните подготовленные изменения в репозитории и получите их на чешском
   компьютере. Перейдите в папку репозитория и проверьте зависимости:

```powershell
python --version
ffmpeg -version
ffprobe -version
git status
python -m unittest discover -s tests -v
python scripts/filter_ru_ua.py
```

4. Для первого небольшого запуска:

```powershell
python scripts/check_ru_ua.py --confirm-direct-cz --max-channels 10 --workers 1 --budget-seconds 600
```

Далее обычный запуск:

```powershell
powershell -NoProfile -File scripts/run-cz-check.ps1
```

Если локальная политика запрещает `.ps1`, используйте прямую команду Python
выше с `--max-channels 120 --workers 2 --budget-seconds 1500`.
Скрипт запускайте в одном экземпляре. Межпроцессная блокировка защищает базу.
Не используйте одновременно разные копии репозитория для записи одной истории.

## Автоматический запуск каждые 6 часов

Добавлен workflow `RU UA catalogue and CZ checks`:

- после успешного существующего `Update IPTV Playlist` обновляет языковой каталог;
- реагирует на изменение источника и ручных настроек;
- запускается также по расписанию `47 */6 * * *` UTC и вручную;
- на GitHub-hosted runner выполняет только фильтрацию и тесты;
- медиа проверяет только на вашем Windows runner с меткой `iptv-cz`.

Настройку runner выполняем позднее. Когда будете готовы:

1. В GitHub откройте Settings → Actions → Runners → New self-hosted runner.
   Выберите Windows/x64, выполните команды регистрации из GitHub на чешском ПК.
   Добавьте custom label `iptv-cz`. Python и FFmpeg должны быть доступны
   именно учётной записи runner; после изменения PATH перезапустите службу.
2. В Settings → Secrets and variables → Actions → Variables добавьте переменную
   репозитория `CZ_CHECKS_ENABLED` со значением `true`.
3. В Actions вручную запустите `RU UA catalogue and CZ checks`.
   У runner должны быть доступ к сети и права GitHub Actions на запись contents.

До включения переменной job проверки полностью пропускается; очередь runner
не ожидается. После включения проверка идёт на scheduled/manual запусках,
не на каждом обновлении каталога. Выключенный компьютер не выполняет проверки,
а расписание GitHub может задерживаться. Платный сервер не требуется; runner
использует ваш ПК и ваш интернет. Для публичного репозитория не добавляйте
триггер `pull_request` к локальному runner: он исполняет код workflow.
Инструкция регистрации:
[GitHub self-hosted runners](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners).

Исходный workflow сохраняет своё расписание и алгоритм обновления.
Добавлена только команда `git pull --rebase` перед его push: два workflow
сохраняют разные файлы, и должны учитывать новые коммиты друг друга.
Конфликт Git останавливает публикацию; принудительный push не используется.

Можно вместо runner создать задание Планировщика Windows с периодом 6 часов
для прямой команды Python. Тогда Git-сохранение результатов выполняйте отдельно:
`git add data playlist-ru-ua-testing.m3u`, добавьте основной файл, когда он
появится, затем `git commit` и `git push`. Автоматический push реализован
в Actions; вспомогательный `.ps1` сам ничего не отправляет в GitHub.

## Как устроены проверки

Запуск требует FFmpeg и подтверждает чешский публичный IP через HTTPS-сервисы
`ipapi.co` и `ipwho.is` до и после партии. Прокси-переменные и системные
HTTP-прокси не используются проверяющим кодом; VPN он не обходит.
В публичной истории сохраняется хеш IP, не домашний IP-адрес.
Если геолокация недоступна, противоречива или IP изменился, партия не принимается.

Для HLS читаются master и вложенные manifest (до четырёх уровней), доступные
ключи AES-128, initialization map и три разных медиасегмента. Проверяется
вариант с наибольшим заявленным размером изображения, затем полосой; фактические
характеристики подтверждает FFprobe. Это не обещание
доступности всех качеств внутри adaptive master. До 1 МБ с каждого сегмента
скачивается для диагностики скорости. Затем FFmpeg действительно декодирует
видео: минимум 10 секунд и 12 кадров, без критических ошибок, не более
24 секунд фактического времени декодирования (жёсткий тайм-аут процесса 30 с).
Один HTTP 200 успехом не является. Скорость и длительность сохраняются.

HTTP 451 и явное сообщение о региональном запрете учитываются как geo.
Обычный 403 без подтверждения причины считается ошибкой, не доказательством
геоблокировки. Ошибка может также зависеть от сервера, заголовков или срока URL.
DRM не обходится. Неподдержанные протоколы, byte-range HLS и специальные
Kodi/DRM-настройки оставляются UNKNOWN_CZ. Записи при этом не теряются.

По умолчанию максимум два одновременных канала, разные исходные хосты в одной
партии, пауза 1 с между партиями, не более 120 каналов или 25 минут за запуск.
Редиректы разных URL могут вести на общий CDN; общая параллельность всё равно
ограничена двумя. Недостаточно времени — прогресс сохраняется, следующий запуск
продолжает с оставшихся каналов. В пределах незавершённого цикла плейлисты
не заменяются. При 708 записях полный цикл может потребовать минимум шесть
запусков, а три цикла — минимум 18 запусков; тайм-ауты увеличивают срок.

## Статусы и защита публикации

- `STABLE_CZ`: три последовательных успешных CZ-наблюдения с промежутками
  минимум 5 часов, каждое с реальным декодированием видео. Шестичасовое
  расписание обычно даёт больший промежуток; при пакетной проверке — ещё больше.
- `GEO_BLOCKED_CZ`: два последовательных подтверждения регионального запрета.
- `OFFLINE`: три последовательные ошибки получения/декодирования.
- `UNSTABLE_CZ`: смесь успешных и неуспешных проверок. Один сбой после
  STABLE_CZ сохраняет прежний статус до повторной проверки; два снимают его.
- `UNKNOWN_CZ`: недостаточно данных, неподдержанный способ проверки либо
  подтверждения устарели. Успешные данные действуют не дольше семи дней.

Для восстановления нужны снова три последовательных успеха. Все наблюдения
сохраняются, но для текущего решения учитывается только семидневное окно.
Это выборочная оценка стабильности, не гарантия непрерывной работы.
Истечение семи дней требует следующего запуска фильтра/проверки: статический
файл сам по себе не обновляется, если оба компьютера/автоматизации выключены.

Основной M3U формируется только из STABLE_CZ. Диагностический — UNKNOWN_CZ и
UNSTABLE_CZ. OFFLINE/GEO_BLOCKED_CZ и исключённые по языку записи остаются в JSON.
При пустом результате прежний файл сохраняется, в отчёте `main_updated=false`:
это аварийная сохранённая копия, а не подтверждение текущего состава STABLE_CZ.
Проверяйте `ru-ua-report.json` перед использованием старой копии.
При частичной проверке, ошибке разбора, FFmpeg/геолокации, скрипта или записи
публикации нет. Обычные ошибки записи откатываются; GitHub коммитит только
после успешного завершения скрипта. При жёстком отключении питания локальной
системы между несколькими заменами файлов восстанавливайте последнюю Git-версию.

Последний отчёт: `data/ru-ua-report.json`. История запусков: `data/reports/`.
Неуспешный запуск пишет отдельный `*-failed.json`, сохраняя последний хороший
отчёт и плейлисты. При полном диске или аварийном завершении процесса запись
такого отчёта также может оказаться невозможной; проверьте журнал Actions.
В базе каждая проверка содержит время, результат, длительность, количество
скачанных данных и подтверждение CZ. Изменившиеся/восстановленные каналы
в отчёте обозначены идентификаторами: по ним находятся полный блок и история
в `ru-ua-state.json`. Отчёты и база входят в Git, автоматической очистки истории нет.

Публичная доступность URL и наличие его в IPTV-org не подтверждают лицензию
на ретрансляцию. Используйте только разрешённые правообладателем потоки;
скрипты не добывают платные ссылки и не обходят авторизацию или ограничения.

## Категории в едином пользовательском M3U

Отдельных плейлистов для разных телевизоров нет. Канал повторяется в нескольких
M3U-записях с разными `group-title`, если принадлежит нескольким категориям.
Поэтому число записей может быть больше числа потоков. Тематические категории
источника переводятся: Movies/Series → Кино и сериалы, Sports → Спорт,
News → Новости, Music → Музыка, Documentary/Science/Education → Познавательные,
Kids/Animation → Детские. Прочие темы сохраняются или переводятся аналогично.

Ручная корректировка тем — `data/category-overrides.json`. Ключ: полный URL,
точный `tvg-id` с `@HD` либо идентификатор без суффикса (в таком порядке):

```json
{
  "Example.us": {
    "groups": ["Кино и сериалы", "Познавательные"],
    "evidence": "Официальное описание программы канала"
  }
}
```

Специальные категории так подделать нельзя: перечисление OLED/4K/HDR в ручной
тематической настройке или названии источника не даёт этих статусов.

- `4K Ultra HD`: измеренные FFprobe ширина ≥3840 и высота ≥2160.
- `HDR`: подтверждён один из HDR10/HDR10+/HLG. Числа для подтипов отчёт
  показывает отдельно, HDR10+ не дублируется в счётчике HDR10.
- Для HDR10 нужны PQ (`smpte2084`), BT.2020, минимум 10 бит, mastering display
  metadata и content light level metadata. Для HDR10+ нужны PQ/BT.2020/10+ бит
  и динамические метаданные SMPTE2094-40. Для HLG — `arib-std-b67`, BT.2020,
  минимум 10 бит. Это консервативные правила: если side data недоступны,
  канал может не попасть в HDR, хотя телевизор распознаёт HDR самостоятельно.
- FFprobe изучает stream и четыре секунды декодированных кадров; FFmpeg
  подтверждает воспроизведение того же выбранного варианта. Данные сохраняются
  только у успешной проверки, не выводятся из имени. 4K SDR получает 4K, без HDR.
  Если FFprobe отсутствует или не смог прочитать свойства, характеристики
  неизвестны. Для специальных категорий используются последние успешные
  измерения не старше семи дней; это не проверка всех передач канала.
- `OLED`: только ручное визуальное подтверждение минимальной постоянной
  графики в `data/oled-channels.json`. Пример структуры (замените фиктивный ID):

```json
{
  "Example.us@HD": {
    "approved": true,
    "reviewed_at": "2026-11-11T12:00:00+01:00",
    "expires_at": "2026-12-11T12:00:00+01:00",
    "evidence": "Просмотрены несколько передач: постоянного экранного логотипа и бегущей строки нет"
  }
}
```

`expires_at` необязателен; `reviewed_at` и объяснение обязательны. Отсутствие
`tvg-logo` ни на что не влияет. OLED-отбор не гарантирует отсутствие статичной
графики во всех будущих передачах и не является гарантией защиты экрана.

В текущем снимке подтверждённых 4K/HDR10/HDR10+/HLG/OLED — по нулю:
реальные потоки ещё не измерялись, ручной OLED-список пуст.

## Исключение специализированных эротических/порнографических каналов

Каждое обновление проверяет категорию `xxx` в IPTV-org channels API и группу
XXX источника. Это основание исключить специализацию канала из всех выходных
групп, включая OLED/4K/HDR и диагностический M3U. Запись и история остаются в базе.
В текущем исходном снимке таких исключений — 0. Это результат известных
классификаций, не покадровая проверка содержания всех телеканалов.

Один `is_nsfw` без категории xxx отправляет специализацию на ручную проверку;
до решения канал остаётся в базе и не публикуется. Пометки 18+, жанры ужасов,
триллеров, боевиков и криминального кино сами по себе не исключают канал.
`data/review-needed.json` содержит списки для ручной проверки языка и специализации.

Ручные решения — `data/content-overrides.json`, ключ: URL либо ID без суффикса:

```json
{
  "Example.us": {
    "decision": "exclude",
    "evidence": "Ссылка на официальное подтверждение специализации канала"
  }
}
```

Решения: `exclude` (подтверждённая специализация), `review` (неоднозначно),
`allow` (подтверждено, что это обычный канал; исправление ошибки источника).
Ручное исправление не отменяет требования языка и STABLE_CZ.

## Проверки разработки и файлы

`python -m unittest discover -s tests -v` проверяет правила и сценарии отказа
на искусственных данных, не присваивая настоящим потокам рабочие статусы.
Оригинальный плейлист сравнивается с Git-версией. Реальное воспроизведение на
Samsung/OTTPlayer, фактическая геодоступность и измерение свойств настоящих
потоков остаются для чешского агента и телевизора.

Основные компоненты: `scripts/filter_ru_ua.py`, `scripts/check_ru_ua.py`,
`scripts/ru_ua_categories.py`, `scripts/ru_ua_content.py`,
`scripts/run-cz-check.ps1`, `.github/workflows/ru-ua.yml`, `tests/test_ru_ua.py`.
Снимки источников, настройки, база, список ручной проверки и отчёты — `data/`.
